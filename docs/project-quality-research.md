## 一、核心工具与方法论调研

### 1.1 RFC (Request for Comments)

#### 简介
RFC 起源于互联网工程任务组（IETF），后被科技公司广泛采用作为技术决策文档格式。用于提出、讨论和记录重大技术变更。

#### 典型结构
- **标题与元信息**：RFC 编号、作者、日期、状态
- **摘要**：一句话概述
- **动机**：为什么需要这个变更
- **提案详情**：技术方案设计
- **备选方案**：考虑过但未采用的方案
- **影响分析**：对现有系统的影响
- **未解决问题**：需要进一步讨论的点

#### 优点
- ✅ 强制深度思考，避免仓促决策
- ✅ 异步协作友好，适合分布式团队
- ✅ 历史可追溯，新成员可快速了解决策背景
- ✅ 鼓励多方参与讨论

#### 缺点
- ❌ 编写成本较高，可能拖慢小型变更
- ❌ 需要团队养成 review 习惯
- ❌ 过度使用会导致文档疲劳

#### 适用场景
- 架构级变更（如引入新技术栈）
- 跨模块影响的功能设计
- 需要多方共识的技术决策

### 1.2 ADR (Architecture Decision Records)

#### 简介
ADR 是轻量级的架构决策记录方法，由 Michael Nygard 提出。每个决策一个独立的 Markdown 文件，存储在代码仓库中。

#### 典型结构（MADR 模板）
```markdown
# ADR-0001: 选择 PostgreSQL 作为主数据库

## 状态
已接受 | 2026-02-19

## 背景
我们需要为 Agent World 选择一个可靠的关系型数据库...

## 决策
使用 PostgreSQL 15+ 作为主数据库

## 理由
- 成熟稳定，社区活跃
- 支持 JSONB，适合半结构化数据
- Supabase 原生支持

## 后果
- 正面：类型安全、事务支持强
- 负面：需要学习 SQL 优化
- 中性：需要配置备份策略
```

#### 优点
- ✅ 极其轻量，5-10 分钟可完成一篇
- ✅ 与代码同仓库，版本控制天然集成
- ✅ 编号系统清晰（ADR-0001, ADR-0002...）
- ✅ 可以标记状态（提议/已接受/已废弃/已替代）

#### 缺点
- ❌ 过于简化，不适合复杂技术方案
- ❌ 缺少讨论过程记录
- ❌ 需要手动维护编号

#### 适用场景
- 技术选型决策（数据库、框架、工具）
- 架构模式选择（微服务 vs 单体）
- 编码规范约定

### 1.3 PRD (Product Requirements Document)

#### 简介
产品需求文档，由产品经理编写，定义"做什么"而非"怎么做"。是产品、设计、工程团队的协作基础。

#### 典型结构
- **目标与背景**：为什么做这个功能
- **用户故事**：作为[角色]，我想要[功能]，以便[价值]
- **功能需求**：详细的功能点列表
- **非功能需求**：性能、安全、可用性要求
- **成功指标**：如何衡量功能是否成功
- **原型/线框图**：视觉参考
- **优先级**：P0/P1/P2 分级

#### 优点
- ✅ 产品视角，关注用户价值
- ✅ 跨职能团队协作的共同语言
- ✅ 明确范围，防止需求蔓延

#### 缺点
- ❌ 编写耗时，需要产品思维
- ❌ 技术细节不足，工程师仍需补充设计文档
- ❌ 容易过时，需要持续维护

#### 适用场景
- 新功能开发前的需求定义
- 跨团队协作的大型项目
- 需要向非技术人员说明的场景

### 1.4 Speckit

#### 简介
Speckit 是一个现代化的项目规范工具，旨在帮助团队标准化技术文档流程。它提供模板库、版本控制集成和协作功能。

#### 核心特性
- **模板系统**：预置 RFC、ADR、PRD 等常见文档模板
- **CLI 工具**：命令行快速创建规范文档
- **Git 集成**：自动编号、状态管理
- **Markdown 优先**：纯文本，易于版本控制

#### 优点
- ✅ 降低文档编写门槛，提供脚手架
- ✅ 统一团队文档风格
- ✅ 自动化编号和索引生成

#### 缺点
- ❌ 需要额外学习工具使用
- ❌ 可能过度工程化（对小团队）
- ❌ 依赖特定工具链

#### 适用场景
- 中大型团队需要标准化流程
- 多项目组织需要统一规范
- 希望自动化文档管理的团队

---

### 1.5 OpenSpec

#### 简介
OpenSpec 是一个开源的项目规范方法论框架，强调"规范即代码"理念。通过结构化的 YAML/JSON 定义项目需求和架构。

#### 核心理念
- **机器可读**：规范文档可被工具解析和验证
- **单一数据源**：从规范生成文档、测试、代码骨架
- **版本化**：规范变更可追踪、可回滚
- **协议优先**：定义接口契约，支持并行开发

#### 优点
- ✅ 支持自动化测试和代码生成
- ✅ 前后端可基于规范并行开发
- ✅ 强制接口契约，减少集成问题
- ✅ 适合 API 驱动的项目

#### 缺点
- ❌ 学习曲线陡峭，需要理解 schema 定义
- ❌ 过度结构化，不适合快速原型
- ❌ 需要配套工具链支持

#### 适用场景
- 微服务架构项目
- 前后端分离的 API 项目
- 需要自动化测试的系统
- 多团队协作的大型项目

## 二、AI Agent 协作项目最佳实践

### 2.1 特殊挑战

AI Agent 协作项目与传统软件项目的关键差异：

1. **异步性更强**：Agent 可能在不同时间、不同上下文中工作
2. **上下文共享**：需要明确的文档让 Agent 快速理解项目状态
3. **决策透明度**：Agent 做出的技术决策需要可追溯
4. **协议优先**：Agent 间通过明确的接口/协议协作

### 2.2 推荐实践

#### 实践 1：CLAUDE.md 作为项目入口
在项目根目录放置 `CLAUDE.md`，包含：
- 项目概述和目标
- 技术栈和架构图
- 目录结构说明
- 开发规范和约定
- 常用命令和工作流

#### 实践 2：轻量级 ADR + 任务驱动 RFC
- **ADR**：记录所有技术选型和架构决策
- **RFC**：仅用于复杂功能设计（跨模块、高风险）
- **任务文档**：每个大任务一个 Markdown 文件，包含背景、目标、验收标准

#### 实践 3：API-First 设计
- 使用 OpenAPI/TypeScript 类型定义接口契约
- Agent 可基于契约并行开发
- 自动生成 API 文档和类型检查

#### 实践 4：自动化验证
- Pre-commit hooks 检查文档完整性
- CI 验证 ADR 编号连续性
- 自动生成文档索引

## 三、Agent World 项目推荐方案

### 3.1 综合评估

| 方法 | 适用性 | 成本 | 推荐度 |
|------|--------|------|--------|
| ADR | ⭐⭐⭐⭐⭐ | 低 | 必选 |
| RFC | ⭐⭐⭐⭐ | 中 | 可选 |
| PRD | ⭐⭐⭐ | 高 | 可选 |
| Speckit | ⭐⭐ | 中 | 不推荐 |
| OpenSpec | ⭐⭐⭐⭐ | 高 | 后期考虑 |

### 3.2 推荐方案：ADR + 轻量 RFC + API Schema

#### 核心理念
- **轻量优先**：避免过度文档化，保持敏捷
- **渐进式**：从简单开始，按需增加复杂度
- **Agent 友好**：文档结构清晰，易于 AI 解析

#### 三层文档体系

**第一层：ADR（架构决策记录）**
- 用途：记录所有技术决策
- 频率：每个重要决策一篇
- 位置：`docs/adr/`

**第二层：RFC（重大功能设计）**
- 用途：复杂功能的详细设计
- 频率：仅用于跨模块、高风险功能
- 位置：`docs/rfc/`

**第三层：API Schema（接口契约）**
- 用途：定义前后端接口、Agent 间通信协议
- 频率：每个 API 端点
- 位置：`docs/api/` 或代码中的 TypeScript 类型

### 4.4 工作流程

#### 新功能开发流程
1. **需求明确** → 创建 RFC（如果复杂）或直接开始
2. **技术决策** → 创建 ADR 记录关键决策
3. **接口定义** → 编写 TypeScript 类型或 OpenAPI schema
4. **并行开发** → 各 Agent 基于接口契约开发
5. **集成测试** → 验证接口契约
6. **文档更新** → 更新 CLAUDE.md 和相关文档

#### ADR 编写时机
- ✅ 选择技术栈（数据库、框架、库）
- ✅ 架构模式决策（状态管理、路由方案）
- ✅ 编码规范约定（命名、目录结构）
- ✅ 部署策略（CI/CD、环境配置）
- ❌ 小的代码重构
- ❌ Bug 修复
- ❌ 文档更新

#### RFC 编写时机
- ✅ 跨模块的大功能（如任务系统、权限系统）
- ✅ 需要多 Agent 协作的复杂功能
- ✅ 有多种实现方案需要讨论的功能
- ❌ 单文件内的小功能
- ❌ UI 组件开发
- ❌ 简单的 CRUD 操作

### 4.5 自动化工具建议

#### 简单脚本（推荐）
创建 `scripts/new-adr.sh`：

```bash
#!/bin/bash
# 快速创建新 ADR

LAST_NUM=$(ls docs/adr/ | grep -E '^[0-9]+' | sed 's/-.*//' | sort -n | tail -1)
NEW_NUM=$(printf "%04d" $((10#$LAST_NUM + 1)))

read -p "ADR 标题: " TITLE
FILENAME="docs/adr/${NEW_NUM}-${TITLE// /-}.md"

cp docs/adr/template.md "$FILENAME"
sed -i "s/XXXX/$NEW_NUM/" "$FILENAME"
sed -i "s/\[简短标题\]/$TITLE/" "$FILENAME"

echo "已创建: $FILENAME"
```

#### Git Hooks
创建 `.git/hooks/pre-commit`：

```bash
#!/bin/bash
# 检查 ADR 编号连续性

ADR_NUMS=$(ls docs/adr/ | grep -E '^[0-9]+' | sed 's/-.*//' | sort -n)
EXPECTED=1

for NUM in $ADR_NUMS; do
  if [ $((10#$NUM)) -ne $EXPECTED ]; then
    echo "错误: ADR 编号不连续，期望 $EXPECTED，实际 $NUM"
    exit 1
  fi
  EXPECTED=$((EXPECTED + 1))
done
```

## 五、总结与建议

### 5.1 核心建议

**对于 Agent World 项目，推荐采用：**

1. **ADR 作为核心**：轻量、快速、易维护
2. **RFC 作为补充**：仅用于复杂功能设计
3. **TypeScript 类型作为契约**：前后端接口定义
4. **CLAUDE.md 作为入口**：Agent 快速了解项目

**不推荐：**
- ❌ Speckit：工具依赖过重，学习成本高
- ❌ 完整 OpenSpec：当前阶段过度工程化
- ❌ 传统 PRD：团队规模小，产品需求可直接沟通

### 5.2 成功关键

1. **保持轻量**：宁可少写也不要写得太复杂
2. **及时记录**：决策后立即写 ADR，不要拖延
3. **持续维护**：定期 review 和更新文档
4. **工具辅助**：使用脚本降低文档编写门槛

### 5.3 预期收益

- ✅ 新 Agent 加入时快速了解项目历史
- ✅ 技术决策可追溯，避免重复讨论
- ✅ 减少 Agent 间沟通成本
- ✅ 提升项目专业度和可维护性
